# Curl.Engine.UnitLibrary

The managed transfer engine (ADR-0506): the code that runs a transfer, moving out of
`Curl.Console` so that `Curl.Console`, `Curl.Api` and `Libcurl` can all drive it. Namespace
`Curl.Engine`. The sections below record, task by task (BL-2285 onwards), what moved here and what
stayed in `Curl.Console` because it is the curl tool's.

It must never reference `Curl.Cli.UnitLibrary` (BL-2310 dropped the last reference): the engine
reads only the easy option groups (`Curl.Api`'s `Easy*Options` records and the engine's own
`EngineToolOptions`, `EngineTransferSettings` and `EngineTraceComponents`, the run's `--trace-config`
components with the ones `-vv` and up add), which `Curl.Console` builds from the command line.

Never reference `Curl.Console`, `Libcurl` or `Curl.Api`: the engine sits beneath all three.

Held to the four quality gates in the root `CLAUDE.md`. Its tests live in `Curl.Engine.UnitTests`.

## What has moved here so far (BL-2285)

`EngineComposition.CreateProtocolHandlers` gives every handler an
`EndPointRecordingConnector` and an `EndPointRecordingDatagramConnector` sharing one
`ConnectionEndPointRecorder`, and wraps each handler in an `EndPointReportingProtocolHandler`, which
puts the end points of the transfer's first connection (FTP's control connection) on its report when
the handler reported neither, so `%{local_ip}`, `%{local_port}`, `%{remote_ip}` and `%{remote_port}`
work for every scheme without handler code; HTTP keeps its own (ADR-0119, BL-515). Each handler sits
behind a `LazyProtocolHandler` that names its schemes and builds the handler on its first transfer
(BL-1715, AF-0063); `EndPointReportingProtocolHandler.Handler` gives the built handler.

An `ftp` or `ftps` URL is claimed by `RoutingFtpProtocolHandler`, which hands an `ftp` one to the HTTP
handler when its proxy is `Http` or `Http10` and `-p` is not given, so it is forwarded to the proxy
as `GET ftp://host/path` with `Host: host:21` (ADR-0056, rule 3; BL-344); any other transfer goes to
`FtpProtocolHandler`.

The trace-event decorators `ClientReaderResetTraceEvents` (the `[READ] client_reset, clear readers`
line before a finished transfer's `left intact` or `shutting down connection` line and after each
followed redirect's `Issue another request to this URL` line; ADR-0357's BL-1159 amendment),
`ClientWriterTraceEvents`, `ConnectReplyHeadWritingEvents` and `ResponseWaitTimerTraceEvents` (the
response wait's `[TIMER]` lines after `Request completely sent off` when the multi is not traced;
ADR-0401, BL-1258) wrap an `ITransferEvents`. `LateBoundDiagnosticLog` is an `IDiagnosticLog` bound
once the runner has opened the run's log.

Four types the plan listed here stay in `Curl.Console` because each uses a tool-side type that has
not moved yet: `ConnectionIdRecordingTransferEvents` and `TlsResultRecordingTransferEvents` (both use
`RunningTransferState`), `MultiStateTraceEvents` (uses `TransferTimers` from `Curl.Engine` and other tool-side types) and
`GatedDiagnosticLog` (uses `WriteGate`).

## Authentication and security-context sources (BL-2286)

`TransferCredentialLookup` then chooses the transfer's credentials, once per URL. When `-u` gives
no user name, the URL's percent-decoded user name and password are sent (`http://zz@host/` sends
`zz:`, `http://:x@host/` sends `:x`, `http://@host/` nothing), replacing a `-u :pw` whole (BL-791).
Under `-n`, `--netrc-file` or `--netrc-optional` the netrc file has its say too, and the runner keeps them as the running transfer's
`LookedUpCredentials`, which `TransferContextFactory` puts on every attempt's context in place of
`-u`'s. A `-u` with a user name wins and no file is read. The file is the `--netrc-file` one, else the one a
non-empty `NETRC` names (BL-2114), else `.netrc` in `HOME` (on Windows `_netrc` after it, and `USERPROFILE` when `HOME` is not set), read
through the runner's `IDataFileReader` and environment. The URL's percent-decoded user name picks
the entry (`Curl.Authentication`'s `NetrcFile`), whose password beats the URL's; an entry with no
login takes the URL's user name, and one with no password sends an empty one, never the URL's
(BL-1356); with no entry the URL's user and password are sent. Under `--netrc-optional` a URL
with a password is not looked up at all, and its own credentials are sent (upstream test381,
BL-1986). A NUL byte in the file ends its line (upstream test793). A required file that is missing or malformed fails each URL with
`curl: (26) .netrc error: no such file` or `syntax error` before anything is sent, `-v` writing
the same text as an info line first (BL-1447);
`--netrc-optional` ignores both. When the file is in use, `TransferCredentialLookup.ForRedirectHops`
gives `RedirectFollower` the same lookup for each redirect hop's URL, so every hop sends its own
host's entry or none, `--location-trusted` or not (BL-790). Measured on curl 8.21.0 (BL-505 Notes).
URL credentials that percent-decode to a byte below 0x20 (only `%00` for `http`, `https`, `ws` and
`wss`) fail with `curl: (3) error extracting credentials from URL` before connecting, a redirect
hop's too, and a matching netrc entry holding one with `curl: (26) control code detected in .netrc
credentials` except over those four schemes; `-v` writes each as an info line first (BL-1411).

The other types moved with it, in `Curl.Engine`: `AwsSigV4HttpAuthenticator` signs every request
with `--aws-sigv4` in place of the ranked schemes (`HttpRequestOptions.AwsSigV4`, ADR-0243) and
`HttpSignatureHttpAuthenticator` signs with the `--httpsig-*` options' `Signature-Input` and
`Signature` lines in place of all of them (`HttpRequestOptions.HttpSignature`, BL-2182, ADR-0485);
`HttpSignatureSetup` runs curl 8.22.0's setup checks for those options at each URL, refusing with
exit 2, 26 or 43 and its `errorf` line. `HandBuiltKerberosSources` reads `krb5.conf` and the
credential cache from disk (`KerberosDiskFileReader`, `KerberosDiskFileWriter`) only when a
hand-built context first asks (BL-527, ADR-0176); `HandBuiltNtlmSecurityContextFactory` answers NTLM with the
hand-built factory on every platform, other schemes with the router (BL-1858); `LateBoundSecurityContextFactory` is an `ISecurityContextFactory` bound
once the connectors exist (ADR-0270); `NegotiateOptionsMapping` and `Socks5AuthenticationMapping`
map the `--negotiate` and `--socks5-*` options to their settings (ADR-0276, BL-615); `NoCryptoEngines`
is what `--engine` does with no crypto engines (ADR-0151).

`NoCryptoEnginesTests` and `Socks5AuthenticationMappingTests` stay in `Curl.Console.UnitTests`
because each drives `CurlCommandRunner` or `CurlComposition`, which are tool-side.

The per-transfer stores moved too (BL-2287), in `Curl.Engine`: `CookieEngine` is the cookies of
one run, as curl's tool sets them up from `-b`, `-c` and `-j`; `HstsTransferPolicy`'s test clock
is `FixedWallClock` and `ClockOverridingHstsStore` (a `CURL_TIME` of whole seconds, ADR-0493);
`SshKnownHostsFileSearch` finds the known-hosts file a scp or sftp transfer checks (ADR-0122);
`CRuntimeErrorNumbers` words a C runtime errno as `strerror` does; and `CurlErrorBuffer` cuts a
message to curl's 255-byte error buffer (ADR-0072; `Curl.Networking` has its own internal copy).

`TlsSessionFileLines`, with its tests, stays in `Curl.Console` because it uses tool-side types
(`ToolNotes`). `HstsCacheFile` stayed too until BL-2291 gave it its own `0666` create mode in
place of `DeferredOutputFileStream.CreateMode` and moved it here. `CookieEngineTests` uses its own read-only file system fake,
and `SshKnownHostsFileSearchTests` links `InMemoryDataFileReader` from `Curl.Console.UnitTests`.

## The engine's composition (BL-2289)

`EngineComposition` builds the engine's services with plain constructor calls - no container, no
reflection, so native AOT sees every type: the protocol handlers (`CreateProtocolHandlers`), the
transports (`CreateTransports`, `CreateTcpConnector`, `CreatePoolingConnector`,
`CreateUdpDatagramConnector`, `CreateDatagramConnectorQuicDialer`), the DNS resolvers
(`CreateDnsResolver`, `CreateDohResolver`, `DnsServerVariableResolverOf`), the TLS providers
(`CreateTlsProvider`), the security-context factories and authenticators
(`CreateSecurityContextFactory`, `CreateDialingSecurityContextFactory`, `CreateHttpAuthenticator`,
`CreateSaslAuthenticator`), the `--trace-config` predicates (`Traces*`) and the option readers
(`AddressFamilyOf`, `ConnectTimeoutOf`, `LocalBindingOf`, `PreProxyOf`, `UnixSocketOf` and the
like). `Curl.Console`'s `CurlComposition` keeps `CreateRunner` and calls these. curl's easy error
text lives in `Libcurl/Misc/ErrorText` (`CurlEasyErrorText`, which `Curl.Console` passes in; the engine never references `Libcurl`), so the DoH
resolver's text comes in through the `easyErrorText` parameter of `CreateTransports`,
`CreateDnsResolver` and `CreateDohResolver`; without one it is empty. `OptionGroupConnectionSettings`
and `ProcessUserId` moved here with it.

What the factories do, moved from `Curl.Console/CLAUDE.md` (BL-2322):

`CreateTransports` wraps an option group's `TcpConnector` in one `PoolingConnector`,
which every TCP handler connects through, so a later URL to the same pool key reuses an
earlier URL's connection; `Curl.Engine`'s `TransferDispatch` holds it as its `ConnectionPool`. In production the
connector shares the run's `ConnectionCache`, which the runner closes without writing anything once
the run's transfers end, whatever their outcome (ADR-0050, BL-334, ADR-0285); a connector made
without one owns its pool, which disposing the dispatch closes. It also holds the `TcpConnector`'s
`LoadResolveEntries`, which the runner calls at the start of every URL's transfer, just before
the `-b` files load, so `-v` prints the `--resolve` entries' `Added ... to DNS cache` lines for
each URL; a `--retry` attempt and a followed redirect reload nothing, as in curl 8.21.0 (BL-486).
The origin's and the HTTPS proxy's TLS providers come from `CreateTlsProvider`,
which builds `HandBuiltTlsProvider` when `TlsClientRouting.Choose` routes the options to the
hand-built client (a `--tls-max` of 1.0 or 1.1 today) and `SslStreamTlsProvider` otherwise
(ADR-0140, ADR-0162, BL-708).

`CreateProtocolHandlers` builds the handlers behind the engine's end-point recorders and `LazyProtocolHandler` (ADR-0119, BL-515, BL-1715, AF-0063).

Their tests are `EngineComposition*Tests` in `Curl.Engine.UnitTests` (with their own copies of the
`LoopbackDnsResolver` and `ScriptedTcpDialer` fakes, and a reference to `Curl.Original.Protocol.Ssh.UnitTests`
for its in-memory SSH server) and `EngineCompositionDnsServersIntegrationTests` in
`Curl.Engine.IntegrationTests`. Tests that run a transfer through `CurlComposition.CreateRunner`,
`CreateTransferDispatch` or `CreateDispatcher` stay in `Curl.Console.UnitTests` as
`CurlComposition*Tests`.

## The transfer context and dispatch (BL-2290)

`TransferContextFactory` builds the `TransferContext` of each URL of an accepted command line,
carrying every option a handler reads: the clock, the run's diagnostic log and HSTS store (both set
by the runner once it has opened them), the `-Y`/`-y` and `-m` watchdogs' wrapped output, progress
sink and cancellation token, the `-D`/`-i`/`-I` header output (`HeaderLineTeeStream` writes each line
to the `-D` output and then the body output) and the `CONNECT` reply heads. Standard input comes in
through its constructor, for a `telnet` transfer's upload. `TransferDispatch` holds one option
group's dispatcher, cookies, proxy selector, connection pool and `--resolve` loader, which the
runner disposes when the group ends; `CurlCommandRunner` receives a
`Func<CommandLineOptions, TransferDispatch>` that returns it.

`AltSvcTransferCache` moved with the factory (the factory stores it on `HttpRequestOptions.AltSvcStore`
and asks it for the route), so the earlier note that it stays in `Curl.Console` no longer holds; it
carries its own copy of the `0666` create mode `DeferredOutputFileStream.CreateMode` holds, so it no
longer reaches a tool-side type.

Their tests moved too: `TransferContextFactoryTests`, `TransferContextFactoryMailTests`,
`AltSvcTransferCacheTests` and `HeaderLineTeeStreamTests` are in `Curl.Engine.UnitTests`, linking
`ManualTimeProvider` and `SteppingTimeProvider` from `Curl.Console.UnitTests`.

## The transfer performer (BL-2291)

`TransferPerformer` (`TransferPerformer.cs` and `TransferPerformer.Setup.cs`, built in `Curl.Console`
by BL-2282 to BL-2284) is here: one attempt under its watchdogs, the run's `%{xfer_id}` and
`%{conn_id}` numbering, and the per-transfer setup and cleanup libcurl does. What it keeps about a
running transfer is `EngineTransferState` (the attempt's watchdogs, the retry and connection IDs, the
looked-up credentials, the SSH options and the alt-svc cache); `Curl.Console`'s `RunningTransferState`
derives from it and adds the tool's part. curl's easy error text comes in through the constructor's
`easyErrorText` (`CurlEasyErrorText.Of` in production, which lives in `Libcurl/Misc/ErrorText` and which `Curl.Console` passes in), so
`KnownHostsFileMissingFailure` is one per performer and `ResolveSshOptionsAsync` and
`SetupFailureAsync` are instance methods. `HstsCacheFile` and `UrlEffective` (`%{url_effective}`,
which the HSTS switch line prints) moved with it. `TransferPerformerTests` and `UrlEffectiveTests`
are in `Curl.Engine.UnitTests`; the setup tests use their own `ReadRecordingFileSystem` fake, as
`Curl.Console.UnitTests`' `InMemoryFileSystem` uses tool-side types.

## The network option group (BL-2323)

`Curl.Engine.UnitLibrary` references `Curl.Api.UnitLibrary` for its option records. `EngineComposition`'s transport, TCP connector, pooling connector and DNS resolver factories take `EasyNetworkOptions` beside `CommandLineOptions` (then still read for TLS, proxy, trace, HTTP version and `-m`; BL-2324, BL-2325 and BL-2350 moved TLS, proxy and the HTTP version to their records), and `CreateUdpDatagramConnector`, `LocalBindingOf`, `UnixSocketOf`, `AddressFamilyOf`, `ConnectTimeoutOf`, `DnsServerVariableResolverOf`, `TcpSocketOptionsOf`, `TransferTimers.Of` and `OptionGroupConnectionSettings.Of` read their network settings from it alone (ADR-0526). `Curl.Console` builds the record with `EasyOptionsFromCommandLine.NetworkOf`, which `Curl.Engine.UnitTests` and `Curl.Engine.IntegrationTests` link. `TransferContextFactory.Create` takes it too and reads `--connect-timeout` (the record's zero, not set, becomes a `null` `TransferContext.ConnectTimeout`) and the `--connect-to` mappings `ConnectToTunnelsThroughProxy` checks from it (BL-2343); `-m` still comes from `EasyTransferOptions`.

## The TLS option group (BL-2324)

`TlsClientOptionsMapping` (`Of`, `ProxyOf`, `DohOf`), `TlsBuildInformation`, `CreateTransports`, `CreateDnsResolver`, `CreateDohConnector`, `CreatePoolingConnector` and `OptionGroupConnectionSettings.Of` read TLS settings from `EasyTlsOptions`, which `Curl.Console` builds with `EasyOptionsFromCommandLine.TlsOf`; `--no-alpn` and `--ssl-sessions` still come from `CommandLineOptions` (ADR-0530).

## The form body (BL-2344)

`MultipartFormPartMapping.FromMimeBody` builds the builder's parts from `EasyHttpOptions.MimePost`, which `Curl.Console` builds with `EasyOptionsFromCommandLine.HttpOf`: an `EasyMimeFile` or `EasyMimeStandardInput` part with a file name is an upload, one without is file content, `EasyMimeBytes` is UTF-8 text when it is valid UTF-8 and raw bytes otherwise, `EasyMimeCallback` is a reader part (BL-2470), and `SubParts` is a multipart. `NameEscapingOf` and `RequestContentTypeOf` still read `CommandLineOptions` (ADR-0531).

## The HTTP request, version and redirect mappings (BL-2345)

`HttpRequestOptionsMapping.Of`, `RedirectPolicyMapping.Of` and `TransferContextFactory.Create` take `EasyHttpOptions` for the headers (with `--json`'s), `-A`, `-e`, `--request-target`, the `-d` body (`PostFields`, `null` under `-G`), the encodings (`Compressed` is a set `AcceptEncoding`, `PassesContentCoding` is set from `!HttpContentDecoding` and `PassesTransferCoding` from `!HttpTransferDecoding`, each on its own, ADR-0780), `-L`/`--follow`, `--max-redirs`, `--post30x`, the HTTP version, `--http0.9`, `--ignore-content-length` and `--expect100-timeout`; proxy headers, `--unix-socket`, `--happy-eyeballs-timeout-ms` and the `--proto` options still come from `CommandLineOptions`, and authentication from `EasyAuthenticationOptions` (BL-2352). `HttpVersionMapping` maps `Curl.Api`'s `HttpVersion` (ADR-0532). `CreateTransports`, `CreateTcpConnector`, `CreatePoolingConnector` and `OptionGroupConnectionSettings.Of` take `EasyHttpOptions` beside the other groups, and the ALPN list, `HttpsConnectFirstAttemptVersionOf` and the HTTPS-CONNECT second attempt read its `HttpVersion` (BL-2350); `--no-alpn` and `--ssl-sessions` still come from `CommandLineOptions`.

## The cookie, alt-svc and HSTS settings (BL-2346)

`CookieEngine.FromHttpOptions`, `AltSvcTransferCache.OpenAsync`, `HstsCacheFile.ReadAsync` and `WriteAsync`, and `TransferPerformer`'s `SwitchToHttpsForHstsAsync`, `OpenAltSvcCacheAsync` and `WriteCookieJarAltSvcAndHstsFilesAsync` take `EasyHttpOptions` for `-b` (`Cookie`, the strings joined as curl's `cookie_setopts` joins them, and `CookieFiles`), `-c`, `-j`, `-H` (an `-H` naming `Cookie` drops the strings), `--alt-svc`, the HTTP version the alt-svc lookup keys on, and `--hsts`; the `-G` / `--url-query` query, `--path-as-is` and `--connect-to` still come from `CommandLineOptions` (ADR-0533).

## The behaviour and transfer settings (BL-2347)

`TransferContextFactory.Create` takes `EasyBehaviourOptions` (`-i`) and `EasyTransferOptions` beside `EasyHttpOptions` for the `-r` text, `-I`, `-R` (`FileTime`), `-z` (`TimeValue` in whole seconds, so a date past 9999 keeps its seconds), `-B`, `--crlf`, `--max-filesize` and `-m` (zero is none, as libcurl's), and a `-T` upload under `-C -` (`Upload` with `ResumeFrom` -1, which the runner sets per transfer); `HttpRequestOptionsMapping.Of` reads `-X` and `-f` from them (`--fail-with-body` still from `CommandLineOptions`), `MailRequestOptionsMapping.FromCommandLine` reads `-X`, and `TransferPerformer.StartLowSpeedWatchdog`, `StartMaxTimeWatchdog` and `TransferTimers.Of` read `-Y`/`-y` and `-m` (ADR-0534).

## The protocol settings (BL-2348)

`TransferContextFactory.Create` takes `EasyProtocolOptions` for FTP's `-P`, `-Q` (`Quote`, `PreQuote` behind `+` and `PostQuote` behind `-`, one list the handlers sort by prefix), `-a`, `--disable-epsv`/`--disable-eprt`, `--ftp-pret`, `--ftp-create-dirs`, `--ftp-alternative-to-user`, `--ftp-skip-pasv-ip`, `--ftp-ssl-ccc`, `--ftp-account` and `--ftp-method`, and for `--tftp-blksize` (512 is `null`, not given), `--tftp-no-options` and `-t`; `MailRequestOptionsMapping.FromCommandLine` reads the sender, recipients, `AUTH` and allow-fails from `EasySmtpOptions`; `TransferPerformer.ResolveSshOptionsAsync` and `SshOptionsMapping.Of` read the SSH keys, fingerprints, compression and `--knownhosts` from `EasySshOptions` (`--pass`, `-k`, `-s` and `-S` still from `CommandLineOptions`). `RoutingFtpProtocolHandler`, `CreateFtpProtocolHandler` and `SshKnownHostsFileSearch` read no option (ADR-0535).

## The proxy settings (BL-2325)

`TransferProxySelection.TrySelect`, `EngineComposition.PreProxyOf`, `HaproxyProtocolOf`, `CreateProxyTunnelOptions`, `Socks5AuthenticationMapping.Of` (was `FromCommandLine`), `TransferPerformer.TrySelectProxyAndCredentials` and `TransferContextFactory.Create` (`-p`, `--suppress-connect-headers`) read the proxy, pre-proxy, proxy type, no-proxy list, proxy headers, SOCKS5 and HAProxy settings from `EasyProxyOptions`, which `Curl.Console` builds with `EasyOptionsFromCommandLine.ProxyOf`; `CreateTransports`, `CreateTcpConnector`, `CreatePoolingConnector` and `OptionGroupConnectionSettings.Of` take it beside the other groups. `ProxyType` is the kind of proxy text with no scheme, and `Https2` stays HTTP and asks the tunnel for HTTP/2. `-U` still comes from `CommandLineOptions`, `--proxy-service-name` and `--delegation` from `EasyAuthenticationOptions` (BL-2353), and `--connect-to`'s tunnelling from `EasyNetworkOptions` (BL-2343) (ADR-0536). Their record-driven tests are `EasyProxyOptionsReadingTests`.

## The credential lookup (BL-2338)

`TransferCredentialLookup` (`TryLookUp`, `TryCheckUrlCredentials`, `ForRedirectHops`) and `TransferPerformer.TrySelectProxyAndCredentials` read `-u`, `-n`, `--netrc-file` and `--netrc-optional` from `EasyAuthenticationOptions`, which `Curl.Console` builds with `EasyOptionsFromCommandLine.AuthenticationOf`: `Netrc` and `NetrcFile` choose the file, and `-u` wins when `UserName`, else `UserPassword` up to its first colon, is not empty (ADR-0516). `-U` and `--unix-socket` still come from `CommandLineOptions`. `NegotiateOptionsMapping.Of` (was `FromCommandLine`), `CreateTransports`, `CreateTcpConnector` (SOCKS5 GSS-API) and `CreateProxyTunnelOptions` read the service names, `--delegation` and the proxy's auth methods from it too, `HttpRequestOptionsMapping.ProxyAuthSchemesOf` turning `ProxyAuthentication` back into the tunnel's schemes (`Any` is `Any`, each bit its scheme, Basic when none is left); `CreatePoolingConnector` reads no authentication setting and takes no record (BL-2353). `HttpSignatureSetup.Of`, `HttpRequestOptionsMapping.Of` (the methods, bearer token, AWS SigV4 and HTTP signature), `MailRequestOptionsMapping.FromCommandLine` (login options, SASL, bearer, service name), `RedirectPolicyMapping.Of` (`--location-trusted` as `UnrestrictedAuthentication`, `--disallow-username-in-url`) and `TransferContextFactory.Create` (`-u`'s `UserPassword`, split at its first colon) read it too (BL-2352). `HttpRequestOptionsMapping.AuthSchemesOf` turns its `CURLAUTH_*` bits into the handler's schemes as `CommandLineOptions.AuthSchemes` gives them: `Any` is every scheme the engine knows, Bearer only with `XOAuth2Bearer` set, the `AwsSigV4` bit giving no scheme, and Basic when none is left unless that bit is set (`None`, so a handle whose `CURLOPT_AWS_SIGV4` was set back to `NULL` sends no `Authorization`, upstream test1978, BL-2748). Their record-driven tests are `EasyAuthenticationOptionsReadingTests` and `EasyAuthenticationOptionsMappingTests`.

## The transport factories' tool settings (BL-2356)

`CreateTransports`, `CreateTcpConnector`, `CreatePoolingConnector`, `WaitsForMultiplexing` and `OptionGroupConnectionSettings.Of` take an `EngineToolOptions` (`-Z`, `--parallel-immediate`, `--ssl-sessions` and the `-m` limit the trace timer lines report), which `Curl.Console` builds with `EasyOptionsFromCommandLine.ToolOptionsOf`; ALPN is `EasyHttpOptions.SslEnableAlpn`, `CreateProxyTunnelOptions` takes `EasyHttpOptions` for `-A`, and `CreateDnsResolver`, `CreateDohConnector` and `CreateDatagramConnectorQuicDialer` take no command line. `--interface` is parsed by `EngineInterfaceBinding` (ADR-0538).

## The transfer settings (BL-2357)

`TransferPerformer`'s setup steps (`TryParseTransferUrl`, `RefuseMalformedSetopt`, `TrySelectProxyAndCredentials`, `ResolveSshOptionsAsync`, `LoadCookieFilesAsync`, `SwitchToHttpsForHstsAsync`, `OpenAltSvcCacheAsync`, `SetupFailureAsync`, `WriteCookieJarAltSvcAndHstsFilesAsync`), `TransferContextFactory.Create`, `RedirectPolicyMapping.Of`, `HttpRequestOptionsMapping.Of` and `MailRequestOptionsMapping.FromCommandLine` take an `EngineTransferSettings` for the curl tool's own settings (`-s`, `-S`, `--fail`, `-k`, `--pass`, `--engine`, `--ech`, `-d`, `-U`, `--proto`, `--proto-redir`, the `--ssl*` level, `-l`, `--upload-flags`, `--proxy-header`, `-p`, `--unix-socket`, `--happy-eyeballs-timeout-ms` and the `-G` / `--url-query` query), which `Curl.Console` builds with `EasyOptionsFromCommandLine.TransferSettingsOf`; `--path-as-is`, `--interface` and `--connect-to` come from `EasyNetworkOptions` (ADR-0539).

## The last Curl.Cli types in the mappings and lookups (BL-2358)

`MultipartFormPartMapping.NameEscapingOf` takes whether `--form-escape` was given and `RequestContentTypeOf` the `-H` values; `HttpRequestOptionsMapping.HappyEyeballsTimeoutOf` takes the `--happy-eyeballs-timeout-ms` value; `EngineTransferSettings.UploadFlags` is the names of the `--upload-flags` flags set, in curl's order, which `Curl.Console` works out (`EasyOptionsFromCommandLine.TransferSettingsOf`) so `MailRequestOptionsMapping` no longer names `ImapUploadFlags`. `TransferCredentialLookup` and `SshKnownHostsFileSearch.Find` read files through a `Func<string, byte[]?>` (`null` when unreadable) that `CurlCommandRunner.ReadDataFile` supplies from its `IDataFileReader`, so neither names `Curl.Cli`.

## The managed engine and its easy handle (BL-2316)

`ManagedCurlEngine` is the `ICurlEngine` behind `Curl.Api` and `Libcurl` (ADR-0506, ADR-0541). Its
public constructor runs on the system clock and the real network; the internal one takes a
`TimeProvider` and a `Func<EasyOptions, ProtocolDispatcher>`, which tests use to put a fake
connector under the handlers. Its connection, TLS session and DNS caches are fields of the engine
object, never static, so two engines in one process share nothing; `DisposeAsync` closes its pooled
connections. `CreateDispatcher` builds a transfer's dispatcher as `Curl.Console`'s composition
builds an option group's: `EngineComposition.CreateTransports` over the handle's easy groups and the
engine's caches, then `CreateProtocolHandlers` over its pooling connector. `CreateMulti`
gives a `ManagedMultiTransfer` (BL-2424, below), `CreateUrl` a `ManagedCurlUrlHandle` (BL-2436 and BL-2437, below), `CreateShare` a `ManagedShareHandle` (BL-2434, below), `CreateMime` a `ManagedMimeBuilder` (BL-2439, below)
and `CreateForm` a `ManagedFormBuilder` (BL-2440, below).

`ManagedEasyTransfer` is its `IEasyTransfer`. `PerformAsync` reads `EasyNetworkOptions.Url` (none is
`CurlCode.UrlMalformat` with `No URL set`, one that does not parse the same code with libcurl's
malformed-URL text), builds the context with `TransferContextFactory.Create` from the easy groups and
`TransferSettingsOf`'s `EngineTransferSettings` (what the easy groups say for verify-peer, the key
password, the crypto engine, the proxy tunnel and the Unix socket, libcurl's defaults for the rest),
and performs the attempt with `TransferPerformer.FollowWatchingSpeedAsync` through a
`RedirectFollower`. Body bytes go to `EasyCallbackOptions.Write` and header lines to

## The tool's settings and the engine-wide state (BL-2359)

`ManagedEasyTransfer.TransferSettingsOf` maps the easy options libcurl has a `CURLOPT_*` for onto `EngineTransferSettings`: `EasyNetworkOptions.Protocols` and `RedirectProtocols` (`ProtocolSetOf`: comma-separated, trimmed, lower cased) as `--proto` and `--proto-redir`, `EasyTransferOptions.DirListOnly` as `-l` and `EasyProxyOptions.ProxyHeaders` as `--proxy-header`. The internal `ToolSettings` replaces them whole when set: it is for `Curl.Console` to set from `EasyOptionsFromCommandLine.TransferSettingsOf` once its runner performs through the engine (BL-2318), for the settings that are the tool's alone (`-s`, `-S`, `--fail-with-body`, the `-G` query and the rest); `Duplicate` copies it and `Reset` clears it. Under `EasyTransferOptions.Upload` the handler reads `EasyCallbackOptions.Read` through `CallbackReadStream` (0 ends the upload; below 0 or past the buffer is an `IOException` with libcurl's `read function returned funny value`), and with no read callback the upload is empty. What the curl tool's transfers share across one run is the engine's own `ManagedEngineSharedState` (`EngineWide`; library handles run over caches of their own since BL-3271, below): the connection, TLS session and DNS caches, a `CookieStore` every handle's HTTP handler keeps cookies in when `CookieEngine.FromHttpOptions` turns the engine on, an `HstsTransferPolicy` on every context, and a `TransferPerformer` that gives each perform the next `TransferInfo.TransferId` and holds curl's easy error text, which `ManagedCurlEngine`'s internal constructor takes (empty from the public one). The internal constructor's dispatcher factory gets the options, the shared state and the cookie store (ADR-0542).

## The cookie, alt-svc and HSTS files and `%{conn_id}` (BL-2362)

`ManagedEasyTransfer.PerformAsync` does the runner's setup and cleanup around its attempt with `TransferPerformer`'s own steps, in the runner's order: `LoadCookieFilesAsync` (the `-b` files into the shared `CookieStore`), `OpenAltSvcCacheAsync` (the transfer's own `AltSvcTransferCache`, kept on its `EngineTransferState` and put on the context) and `SwitchToHttpsForHstsAsync` (the `--hsts` file read, an `http` URL the cache knows switched to `https`) before connecting, and `WriteCookieJarAltSvcAndHstsFilesAsync` after it, whatever the outcome; the alt-svc file is the exception: the handle keeps its first perform's `AltSvcTransferCache` across performs and `Reset` and writes it in `DisposeAsync`, as `curl_easy_cleanup` does, and a `Duplicate` starts with none (upstream test1908, BL-2671; the engine's host serves alt-svc over `http` when its environment reader sets `CURL_ALTSVC_HTTP`). ## The debug and progress callbacks (BL-2360)

Under `EasyBehaviourOptions.Verbose` with `EasyCallbackOptions.Debug` set, `ManagedEasyTransfer` gives the context a `DebugCallbackTransferEvents`: an info line goes to the callback as `CurlInfoType.Text` with its line feed, a connection opened or reused and a TLS handshake, trust or message as the `Text` lines `-v` prints (`Curl.Output`'s `TransferEventInfoText`, the running platform's build), head bytes as `HeaderOut` and `HeaderIn`, body bytes as `DataOut` and `DataIn`, and TLS record bytes as `SslDataOut` and `SslDataIn` in the OpenSSL build only. ## The curl tool's serial attempts (BL-2318, BL-2394)

## The runner's -v and --trace events (BL-2397)

The internal `ManagedEasyTransfer.ToolEvents` (`EngineToolTransferEvents`: the runner's whole events chain - its `-v` and `--trace` writer, `TraceIdsTransferEvents`, `MultiStateTraceEvents`, its `--trace-config` decorators and `ConnectionIdRecordingTransferEvents` - and the running transfer it keeps) is where a perform from the options reports every event while it is set, in place of `EasyCallbackOptions.Debug` and the `TraceComponents` decorators; the perform runs on its `State` and builds no `EngineConnectionIdTransferEvents`, so `%{conn_id}` is numbered once, by the runner's recorder, and `Info.ConnectionId` is what it kept (`StateAndEventsOf`). `TlsVerifyResultRecordingTransferEvents` no longer wraps it (BL-2394, ADR-0622). ## The runner's progress meter and watchdogs (BL-2398)

The internal `ManagedEasyTransfer.ToolProgress` (`EngineToolTransferProgress`: the runner's `TransferProgressRecorder` and its `-Z` `--fail-early` abort token) is where a perform from the options reports progress while it is set, in place of `EasyCallbackOptions.TransferInfo` and `Progress`; the abort token is linked into the transfer's, and the handle starts fresh `-Y`/`-y` and `-m` watchdogs from `EasyTransferOptions` on the running transfer (`ToolEvents`' state, else its own) through the engine's `TransferPerformer`, writing to `Host.DiagnosticLog`, on every perform, so a `--retry` attempt gets a fresh `-m` and a stalled one ends with the runner's exit 28 text (`ProgressStartingWatchdogsOf`). ## The write, read and header callbacks' pause and abort (BL-2415)

Each `ManagedEasyTransfer` owns an `EasyPauseGate` (the handle's `CurlPause` bits; `Pause` sets them and `PausedDirections` reads them). A write or header callback that returns `WriteCallbackResult.Pause` pauses receiving, and `CallbackWriteStream.WriteAsync` waits under the transfer's token until `Pause` clears that bit, then hands the same chunk over again; a read callback's `ReadCallbackResult.Pause` pauses sending and `CallbackReadStream.ReadAsync` asks again the same way. A `file` URL gets no gate (libcurl's `PROTOPT_NONETWORK`), and the synchronous `Write` and `Read` cannot wait, so a pause there fails with libcurl's `Write callback asked for PAUSE when not supported` (`CURLE_WRITE_ERROR`) or `Read callback asked for PAUSE when not supported`. `ReadCallbackResult.Abort` marks the stream `Aborted`, and the perform answers `CurlCode.AbortedByCallback` with `operation aborted by callback`, also when the handler lets the read's `IOException` escape rather than mapping it, as SMTP's after `DATA` does (`FollowUnlessAbortedAsync`, upstream test1507, BL-2640); `WriteCallbackResult.Error` is a short write (ADR-0573). `EasyPauseGate` counts its `Set` calls (`Unpauses`); each stream reads the count before calling the callback and passes it to `Pause`, which ignores the pause when a `Set` ran since, so an unpause made while the callback was returning its pause is not lost (BL-2518). A `curl_mime_data_cb` part's or `curl_formadd` stream field's `MimeCallbackReadStream` waits on the same gate (`MultipartFormPartMapping.FromMimeBody`'s and `MimePostForm.BuildAsync`'s `pauseGate`), and while a perform waits on the gate its progress callback is called again every `EasyPauseGate.PausedTickInterval` (1 second; `TickWhilePaused`, `CallbackTransferProgress.PausedTickOf`), as `curl_easy_perform` wakes, so an xferinfo callback can unpause the handle (upstream tests 670 to 673, BL-2631, ADR-0685). Their tests are `EasyPauseGateTests`, `CallbackWriteStreamTests`, `CallbackReadStreamTests` and `ManagedEasyTransferTests.Callbacks.cs`.

## The multi handle's event loop (BL-2424)

`ManagedCurlEngine.CreateMulti` gives a `ManagedMultiTransfer`, the engine's `IMultiTransfer`: each added transfer runs as its own `IEasyTransfer.PerformAsync`, started by the next `PerformAsync` of the multi handle, so the transfers run at once over the engine's shared caches. `PerformAsync` never waits: it starts what is new, queues one `CURLMSG_DONE` `CurlMultiMessage` with the transfer's `CurlCode` for each perform that has completed, in add order, but never for one it started in the same call, as libcurl's first perform of an HTTP transfer only begins its connect (upstream test2405, BL-2743), and answers the transfers not yet done; `TryReadInfo` takes the messages oldest first. `ManagedEngineSharedState.MultiOwners` keeps each added transfer's multi handle by reference, so a transfer is in one of the engine's multi handles at a time (`AddedAlready`); `Remove` answers `Ok` for a transfer in none and `BadEasyHandle` for one in another, cancels a running perform and drops its unread message. `DisposeAsync` cancels and awaits every perform, and later calls answer `BadHandle`. Get_handles, waitfds, get_offt, the notifications and the network change came with BL-2427 (below), and the socket-action API with BL-2426 (ADR-0594). Its tests are `ManagedMultiTransferTests`, which drive fake transfers that finish when the test says.

## The multi handle's timeout, wait, poll and wakeup (BL-2425)

`ManagedMultiTransfer` takes the engine's `TimeProvider` and an `IWaitSocketPoller`. `GetTimeout` is 0 while a perform has work (a transfer added and not started, or one finished and not yet reported), else the milliseconds, rounded up, until the first running transfer's `EasyTransferOptions.Timeout` expires, measured from the multi perform that started it, else -1. `WaitAsync` ends when a running perform completes (one ready socket), an extra socket has an event (each one's `ReturnedEvents` set), or at the timeout capped by `WaitTimerMilliseconds` (`GetTimeout` leaving out a transfer timeout already passed, whose perform ends the wait as it ends with exit 28, so a perform-and-poll loop never spins; BL-3206, ADR-0783); with nothing to wait on it returns at once. `PollAsync` waits the whole timeout then, and `Wakeup`, sticky like libcurl's wakeup socket, ends it or the next one. A wait with extra sockets asks the poller again every `SocketPollInterval` (10 ms); the production `SocketWaitPoller` calls `Socket.Poll` with no wait on a `Socket` that does not own the descriptor. A negative timeout is `BadFunctionArgument` and a disposed handle `BadHandle` (ADR-0597). Its tests are `ManagedMultiTransferTests.Timers.cs` and `MultiPollTimeoutWaitTests`, on `TimerManualTimeProvider`, whose timers fire only when the test advances it, and `SocketWaitPollerTests`, on a loopback socket.

## The multi handle's socket action and callbacks (BL-2426)

`SocketActionAsync` and `PerformAsync` share one loop (`MoveTransfersOnAsync`): start what is new, queue each finished transfer's `CURLMSG_DONE`, then, on a socket action only (perform never calls it, as libcurl 8.22.0's does not; CGR-148, BL-3677, ADR-0863), tell `MultiOptions.Socket` of each transfer that started (its real socket, when the handle knows one; a running transfer with no socket the handle knows is told none, as the engine's connections are no descriptors an application could wait on, ADR-0997) or finished (`CurlPoll.Remove` with the value `Assign` gave), and `MultiOptions.Timer` of the next timeout when it changed or after an action on `CurlMultiSockets.Timeout`. While every running transfer waits on its real socket the timer is their earliest deadline; while any other runs (one with no socket the handle knows, or one on a socket wait still computing) it is 0, as libcurl's `Curl_expire(data, 0)` for a transfer that can run on, and it is what brings the application back to see that transfer finish (ADR-0998). `Add` tells the timer 0. The socket and events an action names are not read. A callback's -1 answers `AbortedByCallback` and kills the handle: every later socket action answers `Ok` and the unfinished transfers, moving none on, queuing no message and calling neither callback, while the next perform ends every unfinished transfer with `CurlCode.AbortedByCallback`, one not started never starting, and calls neither callback (CGR-148, ADR-0863; tests in `Cgr148Tests`). `Assign` answers `BadSocket` for a socket the callback was not told of or was told to remove, and `Remove` tells the callback `CurlPoll.Remove` for a transfer with a socket (ADR-0599). Its tests are `ManagedMultiTransferTests.SocketAction.cs`, which drive transfers purely through socket actions and pin the callback sequence.

## The URL handle's get (BL-2436)

`ManagedCurlEngine.CreateUrl` gives a `ManagedCurlUrlHandle`, the engine's `ICurlUrlHandle`, holding a `UrlHandleParts` (one nullable field per part, as upstream's `struct Curl_URL`). `Set` parses a whole URL with `CurlUrl` (`UrlHandleParts.Of`: the written port recovered from the text without leading zeros, the scheme guessed when the text does not start with it) under `CURLU_DEFAULT_SCHEME`, `GUESS_SCHEME` (else `BadScheme`), `PATH_AS_IS` and `DISALLOW_USER`, mapping each `CurlUrlRejection` to its `CurlUrlCode`. `Get` reads every part as curl 8.22.0's `curl_url_get`, with the `CURLUE_NO_*` code for a part not set, and every get flag; `UrlPartText` holds the decode, encode, escape and punycode transforms (ADR-0601). Its tests are `ManagedCurlUrlHandleTests`.

## The URL handle's set, dup and clear (BL-2437)

`Set` with a null value clears the part (`UrlPartSetter.Cleared`; the whole URL clears them all), and with a value sets any part as curl 8.22.0's `curl_url_set` (`UrlPartSetter.Set`, answering a `UrlSetResult`): the scheme, port and host checked with upstream's `CurlUrlCode`s, `CURLU_URLENCODE` escaping, `CURLU_APPENDQUERY` joining with one `&`, `CURLU_NON_SUPPORT_SCHEME` and `CURLU_NO_AUTHORITY`, and the handle unchanged on failure. A whole URL that is not absolute (`UrlRelativeReference.IsAbsolute`) is resolved against the URL held (`UrlRelativeReference.Resolve`, upstream's `redirect_url`); a scheme libcurl does not support (`UrlHandleParts.IsSupportedScheme`) is `UnsupportedScheme` without `CURLU_NON_SUPPORT_SCHEME`; under `CURLU_ALLOW_SPACE` spaces are parsed as `%20` and put back (`UrlHandleParts.WithSpaces`). `Duplicate` is a new handle over the same immutable parts (ADR-0602). Its tests are `ManagedCurlUrlHandleTests.Set.cs` and `UrlRelativeReferenceTests`. Under `CURLU_URLENCODE`, a whole URL's path, query and fragment are encoded as `parseurl` encodes them (`UrlHandleParts.UrlEncoded`). A path set under that flag keeps upstream's `allowed_in_path` characters. A set without it upper-cases the part's `%xx` escapes, as curl 8.22.0 does (BL-2735). A host set alone is checked decoded but kept as given (`%43url.se`, `0xff`), a bracketed one normalised; a blank one under `CURLU_URLENCODE` is `BadHostname`; `CURLU_PUNY2IDN` converts a host holding an `xn--` label anywhere; and a whole URL's host is percent-decoded before `CurlUrlHost` reads it as IPv4, IPv6 or a name (BL-2736).

## The header API (BL-2446)

`ManagedEasyTransfer.Headers` is a `TransferHeaderStore`, the engine's `ITransferHeaders`. A perform from the options of an `http`, `https`, `ws` or `wss` URL writes its header lines through `HeaderRecordingStream`, which records each complete line in the store and passes the write on to the header callback when one is set; other schemes, and the curl tool's `ToolOutputs`, record nothing. The store numbers requests from 0, each status line after a final head starting the next (so each redirect hop is its own request), and tags lines `Informational` under a 1xx status, `Connect` under a CONNECT reply (`ConnectReplyHeadWritingEvents` marks the output through `IConnectReplyHeadMarking`, which `HeaderLineTeeStream` passes to its `-D` side), `Trailer` after a final head and `Header` otherwise, with an `HTTP/2` or `HTTP/3` status line's `:status` as `Pseudo`. `Find` and `Next` are curl 8.22.0's `curl_easy_header` and `curl_easy_nextheader`, `Next` finding its place from the `CurlHeader` it answered before by reference. Every perform and `Reset` forget the headers (ADR-0603). The store also keeps the last status line's status (not a CONNECT reply's) and the final head's last `Content-Length` (`ResponseCode`, `ContentLength`), and on each it calls `ResponseHeadRead`, through which a perform puts both on `Info` before the line reaches the header callback, so a header callback reading `CURLINFO_RESPONSE_CODE` or `CURLINFO_CONTENT_LENGTH_DOWNLOAD_T` sees them as libcurl's does (upstream test1485, BL-2639); with them go the times so far - connect and pretransfer to the connection `EngineConnectionIdTransferEvents` took (0 when the curl tool's runner numbers the connections), starttransfer to the first head line and total to now - as libcurl's are live during the transfer (upstream test1541, BL-2648). Their tests are `TransferHeaderStoreTests`, `HeaderRecordingStreamTests` and `ManagedEasyTransferTests.Headers.cs`.

## The multi handle's handles, wait sockets, counts, notifications and network change (BL-2427)

`GetHandles` lists the transfers added and not removed, in add order. `GetWaitSockets` gives one `CurlWaitEvents.PollIn` socket per transfer whose perform has started and whose message is not queued, that the handle knows (the socket the callback is told of; a transfer with none is left out, ADR-0997), then, while there is any, `ResolverWakeupSocket` (`0x3FFFFFFF`), the threaded resolver's wakeup descriptor `AsynchDNS` without c-ares implies, which a wait never asks `IWaitSocketPoller` about (BL-2743); an array too short is filled as far as it goes with the full count and `OutOfMemory`. `GetInfo` counts `CURLMINFO_*` as curl 8.22.0: current (added, not removed), running (message not queued and not pending), done (message queued), added (every add ever), and pending (not started, held back by a connection limit; BL-2428 below); `None` and unknown numbers are `UnknownOption`. `EnableNotification` and `DisableNotification` keep one bit per number 0 to 31 (`UnknownOption` outside); each perform or socket action queues `InfoRead` when it queues a message with none before it and `EasyDone` for each transfer it finishes, and sends them to `MultiOptions.Notify` after moving every transfer on, before the socket and timer callbacks. Setting `Options` with `NetworkChanged` is an action: `ClearConnections` closes the engine's idle connections (`ConnectionCache.CloseIdleAsync`, which `DisposeAsync` awaits) and `ClearDns` empties its `DnsCache` (`Clear`), through the constructor's two delegates; the value is kept with `NetworkChanged` set back to `None` (ADR-0604). Its tests are `ManagedMultiTransferTests.Counts.cs`.

## The multi handle's connection limits, multiplexing and server push (BL-2428)

Before a perform starts a transfer, `ManagedMultiTransfer.CanStart` counts the connections the running transfers hold: one each, except that under `CurlPipelining.Multiplex` transfers to one origin (scheme, host and port from `System.Uri`, else the URL text) whose URL is `https` and not held to HTTP/1, or that ask for HTTP/2 with prior knowledge, share connections `MultiOptions.MaxConcurrentStreams` at a time (below 1 or past `int.MaxValue` is `DefaultConcurrentStreams`, 100). One that cannot join a multiplexed connection with a stream free starts only within `MaxHostConnections` and `MaxTotalConnections` (0 is no limit); otherwise it is pending: not performed, no socket, no timeout, counted by `TransfersPending` and not `TransfersRunning`. Each perform moves the started transfers on first, so a freed slot goes to a pending one in add order in the same call. `OfferPush` is the engine's `push_promise`: it denies for a disposed handle, a parent not in it, no `MultiOptions.Push`, or a pushed transfer that is null or already added, else the callback decides: `Ok` adds the pushed transfer, `ErrorOut` ends the parent with `CurlCode.Http2` on the next perform, anything else denies. `MaxConnects` is applied each time a transfer's message is queued: the handle calls `ConnectionCache.CloseIdleBeyondAsync` (the constructor's `closeIdleConnectionsBeyond`) with it, or `DefaultConnectsPerTransfer` (4) for each transfer in the handle when it is 0 or less, which closes the oldest idle connections until no more than that many, idle and in use, remain; `DisposeAsync` awaits it (BL-2468, tests in `ManagedMultiTransferTests.MaxConnects.cs`). A server push reaches it (BL-2469): while a transfer is in a multi handle whose `MultiOptions.Push` is set, `ManagedEasyTransfer.PushSinkOf` gives its HTTP handler an `EngineHttp2PushSink` (the dispatcher factory's fourth argument, `ManagedCurlEngine.CreateDispatcher`'s `pushSink`; a test factory of three arguments never sees it), so the handler sends `SETTINGS_ENABLE_PUSH` 1, and each `PUSH_PROMISE` becomes `DuplicateForPush` of the transfer offered to `OfferPush` with the promise's `name:value` lines, a refused push being reset with `RST_STREAM` `CANCEL` by the HTTP session. The pushed transfer's next perform sends nothing: `PushedResponseCopier` gives the pushed head to the header callback a line at a time and the body to the write callback, a failed stream answering `RecvError` (ADR-0605). Its tests are `EngineHttp2PushSinkTests`. Its tests are `ManagedMultiTransferTests.Limits.cs`.

## The share handle (BL-2434)

`ManagedCurlEngine.CreateShare` gives a `ManagedShareHandle`, the engine's `IShareHandle`, which owns its own `CookieStore`, `DnsCache`, `TlsSessionCache`, `ConnectionCache` and `HstsTransferPolicy`. A perform from the options whose `EasyBehaviourOptions.Share` names one is attached to it for the perform (`Attach` / `Detach`) and runs over a `ManagedEngineSharedState` holding the share's cache in place of the engine's for each kind shared (`ManagedEasyTransfer.PerformShared`), so handles of different engines send each other's cookies and reuse each other's connections; the numbering and the performer stay the engine's. `Share` and `Unshare` accept cookies, DNS, TLS sessions, connections, PSL and HSTS, else `BadOption`; every option answers `InUse` while a transfer is attached and `Invalid` after a successful `Cleanup`, which refuses with `InUse` while one is attached and starts closing the shared connections. A handle attaches when its `Options` name the share (`CURLOPT_SHARE`, `ManagedShareHandle.Reattach`) and detaches on `DisposeAsync` or when the option names another, so it is in use from setopt to cleanup, as libcurl's; `Cleanup` answers `InUse` without calling a lock callback (BL-2585, upstream test506). The lock callbacks run as synchronous pairs, always `Single`: `Share` around attach, detach and cleanup, `Cookie` for each `CURLOPT_COOKIELIST` item set and each attached handle's cleanup, each shared kind as a perform takes its cache, and `Cookie` around each call the HTTP handler makes of the shared cookies (`CookieStoreFor`) (ADR-0606). A perform takes them in libcurl 8.22.0's order (BL-2603, ADR-0666): `Cookie` once (twice when `CookieFiles` are set), then `Dns` to prune, look the `host:port` up (`ManagedEasyTransfer.ShareHostKeyOf`) and, the first time the share sees it, add it, the handler's `Cookie` pairs, and one `Dns` pair when done (`LockDnsAtDone`). While connections are shared, `Attach` takes `Connect` three times, four the first time the share sees a `host:port` (`TakeConnections`), `LockConnectionsAtDone` once when the perform ends before `LockDnsAtDone`, and `Cleanup` once more after its `Share` lock (`LockForCleanup`), as libcurl's connection pool does (upstream test1554, BL-2653). An HSTS entry one attached transfer learns switches another's `http` URL to `https` while HSTS is shared. The public suffix list is `Curl.Cookies`' one embedded snapshot, which every transfer of every engine checks against, so it is shared whatever the handle says; while PSL is shared, `Attach` takes it under the `Psl` lock right after the `Share` lock (BL-2435, ADR-0617). Its tests are `ManagedShareHandleTests`.

## The MIME API (BL-2439)

`ManagedCurlEngine.CreateMime` gives a `ManagedMimeBuilder`, the engine's `IMimeBuilder` (`curl_mime`), whose `AddPart` appends a `ManagedMimePartBuilder` (`curl_mimepart`) and whose `Build` gives the `EasyMimeBody`, parts in add order. The part's setters follow curl 8.22.0's `lib/mime.c`: `SetData` copies the bytes, `SetFileData` sets the file and its base name as the file name and answers `ReadError` (keeping both) when the path does not exist, `SetDataCallback` keeps the read and seek callbacks (a null read callback clears the data), `SetEncoder` accepts `binary`, `8bit`, `7bit`, `base64` and `quoted-printable` in any case and answers `BadFunctionArgument` otherwise, `SetHeaders` copies the lines, and every data setter replaces the one before. `SetSubParts` nests another `ManagedMimeBuilder`, built when the part is; it answers `BadFunctionArgument` for another engine's builder, a body another part holds, or the body the part is in or one enclosing it, and replacing or clearing it frees the body for another part. A perform from the options with `EasyHttpOptions.MimePost` and no `ToolInputs` builds the body through `MimePostForm` as the runner builds `-F` (`MultipartFormPartMapping`, `MultipartFormBodyBuilder` in UTF-8 over `Host.FileSystem`, `CURLMIMEOPT_FORMESCAPE` and mail URLs escaping with a backslash) before any setup, posting it as the form body, or uploading it as a MIME mail message to an `smtp`, `smtps`, `imap` or `imaps` URL; a build failure (a file that cannot be opened is `ReadError` with `MultipartFormBodyBuilder.OpenFailedMessage`) ends the perform before anything is sent. The internal `CreateFormBoundary` (curl's random boundary by default; `Duplicate` copies it) lets tests fix the boundary. `MultipartFormPartMapping` maps `curl_mime_data` bytes that are valid UTF-8 to text, which the UTF-8 builder sends as the same bytes and the tool's `-F` text in its platform encoding, and any other bytes to a `MultipartFormPartKind.Bytes` part sent verbatim; a `curl_mime_data_cb` part is a `MultipartFormPartKind.Reader` part over a `MimeCallbackReadStream`, read while the body is sent and, with a known size, not asked again once it has given that many bytes, as curl 8.22.0's `read_part_content` (upstream test554, BL-2613), its size giving the body a `Content-Length` and -1 sending it chunked (with `Expect: 100-continue`, as libcurl). The perform collects those streams as the body is built: a `CURL_READFUNC_ABORT` from any of them ends it with `CurlCode.AbortedByCallback` and `operation aborted by callback`, and one with a seek callback makes the body seekable, a resend rewinding it through `(0, SeekOrigin.Begin)` once it was read (BL-2470, ADR-0627). Its tests are `ManagedMimeBuilderTests`, `MimePostFormTests` and `ManagedEasyTransferTests.Mime.cs`, which compare the whole request with the one the tool sends for the same `-F` parts.

## The form API (BL-2440)

`ManagedCurlEngine.CreateForm` gives a `ManagedFormBuilder`, the engine's `ICurlFormBuilder` (`curl_formadd`, `curl_formget`; dropping it is `curl_formfree`). `Add` reads a call's `CURLFORM_*` options with `FormAddCall` as curl 8.22.0's `FormAdd` does: one `FormFieldInfo` node per field, a further `CURLFORM_FILE` or `CURLFORM_CONTENTTYPE` after a file adding a node for one more file, `OptionTwice`, `Null` (a missing value or one of the wrong .NET type), `IllegalArray` and `UnknownOption` as upstream gives them, and `End` ending the call or the array. `FormPost.Complete` then answers `Incomplete` for a field with no name or value or a file with a content length, `Null` for a NUL inside `CURLFORM_NAMELENGTH`, and types a file or buffer with none by its name's ending, else the node before's type, else `application/octet-stream`; a failed call adds nothing. `Build` gives the parts `Curl_getformdata` makes (`FormPost.ToMimePart`): several files are a part named by the field whose sub-parts are the files, `-` is standard input, `CURLFORM_FILECONTENT` sends no file name, and a `CURLFORM_STREAM` part's data is a `FormStreamData` holding its `CURLFORM_CONTENTSLENGTH` and stream object. A perform from the options with no `MimePost` sends `EasyHttpOptions.HttpPost` (`MimePostForm.BodyOf`; never to a mail URL) exactly as it sends `MimePost`, each `FormStreamData` read through `EasyCallbackOptions.Read` as an `EasyMimeCallback` of that length, 0 being -1 (unknown, sent chunked), and sent empty with no read callback; the stream object is not passed, as a managed read callback has no user pointer (BL-2482, ADR-0651). An `HttpPost` form with no parts (Libcurl's `CURLOPT_HTTPPOST` NULL) is an empty body with no `Content-Type`, posted with `Content-Length: 0`, as curl 8.22.0 leaves the part `MIMEKIND_NONE` (upstream test516, BL-2599). A part, or one of a field's several files, named `-` is an `EasyMimeCallback` of size -1 over the handle's `Host.StandardInput` (`MimePostForm.BodyOf`), so the body goes chunked as `Curl_getformdata`'s `stdin` part does; `ManagedCurlEngine`'s internal constructor's `standardInput` is what every handle it creates reads (the conformance harness passes the case's `<stdin>`), else `EasyTransferHost.Library`'s empty one (upstream test650, BL-2625, ADR-0683). `Serialize` builds the body with `MultipartFormBodyBuilder` over the constructor's `IFileSystem` and boundary (`PhysicalFileSystem` and curl's random one from `CreateForm`) and hands the callback the `Content-Type: multipart/form-data; boundary=...` line, an empty line and the body in pieces of at most `PieceSize` (8192) bytes, blocking on the build as `curl_formget` is synchronous, a stream part empty; a short take or an unreadable file answers 26 (ADR-0618). Its tests are `ManagedFormBuilderTests`, `MimePostFormTests` and `ManagedEasyTransferTests.HttpPost.cs`.

## Connect-only, curl_easy_recv and curl_easy_send (BL-2423)

A perform from the options with `EasyNetworkOptions.ConnectOnly` set to `Connect` (`CURLOPT_CONNECT_ONLY` 1) parses the URL, then `PerformConnectOnlyAsync` connects to its host and port (the scheme's default when none is written), with TLS for the schemes `ConnectOnlyConnection.UsesTls` names, through the connector the internal `ManagedEasyTransfer.CreateConnectOnlyConnector` builds (`ManagedCurlEngine.CreateConnectOnlyConnector`: the transports' `TcpConnector`, not the pool; tests put a fake there, `Duplicate` copies it), sends nothing and keeps the connection in the handle's `ConnectOnlyConnection`, which `Connection` answers. A failed connect answers the connector's code and text. Every later perform and `DisposeAsync` close it; `Reset` keeps it. `ReceiveAsync` and `SendAsync` never wait: a receive starts one read and answers `Again` while it runs, then hands its bytes over, keeping what does not fit; a send hands the bytes to one write-and-flush, answers them all sent, and answers `Again` while that write runs; an `IOException` is `RecvError` or `SendError`; with no connection, or options no longer connect-only, both answer `UnsupportedProtocol`. The proxy `TransferProxySelection.TrySelect` chooses from `EasyProxyOptions` and the proxy environment (a no-proxy host none; see "The handle's own proxy" below) goes on the `ConnectTarget`'s `Proxy`, so the connector tunnels through an HTTP or HTTPS proxy or a SOCKS one first, and unusable proxy text ends the perform with the selector's code and text (BL-2472); `ConnectOnly.WebSocket` came with BL-2443 (below) (ADR-0608). An `ftp`, `ftps`, `imap` or `imaps` URL (`LogsInBeforeConnectOnly`) does not take the raw connect: it runs the normal perform path over `ConnectOnlyLoginDispatcherOf`'s `FtpConnectOnlyHandler` and `ImapConnectOnlyHandler` (`ManagedCurlEngine.CreateConnectOnlyLoginHandlers`, over the same connector), which run FTP's login or IMAP's `CAPABILITY` connect phase and keep the open connection in the same `ConnectOnlyConnection` (upstream tests 597 and 660, BL-2623, ADR-0681). Each connection it keeps is known by its operating system socket (`IConnection.SocketHandle`, CGR-129, ADR-0842), or, for a connection with none (an in-memory one), an engine socket number counting up from `ConnectOnlyConnection.FirstSocket` (`0x60000000`; the first is `FirstSocket + 1`), which `Info` answers as `ActiveSocket` and `LastSocket` while it is open and the options ask for connect-only (-1 otherwise), and a `ManagedMultiTransfer` wait given that number as an extra socket answers it from the connection (`ManagedEasyTransfer.ConnectOnlyReadyEvents`, `ConnectOnlyConnection.ReadyEvents`: `PollOut` while no send runs, `PollIn` once bytes wait, a `PollIn` wait starting the read) for a transfer in the handle, other sockets going to the `IWaitSocketPoller` (upstream test677, BL-2633, ADR-0686). Their tests are `ConnectOnlyConnectionTests` (over `ControlledConnection`, whose reads and writes complete when the test says) and `ManagedEasyTransferTests.ConnectOnly.cs`.

## The seek callback (BL-2417)

Under `EasyTransferOptions.Upload` with `EasyCallbackOptions.Seek` set, the upload is a `SeekingCallbackReadStream`, the `CallbackReadStream` that implements `Curl.Protocol.Abstractions`' `IUploadRewinder`: once the read callback has given bytes (`BytesReadSinceRewind`), a followed redirect or an authentication retry that resends the body calls the seek callback with `(0, SeekOrigin.Begin)`, and any result but `SeekResult.Ok` fails the perform with `CurlCode.SendFailRewind` and `seek callback returned error <n>`, as curl 8.22.0's `cr_in_rewind` does. Its tests are `CallbackUploadResumeTests` and `ManagedEasyTransferTests.Callbacks.cs`.

## The socket callbacks (BL-2418)

When a handle sets `EasyCallbackOptions.OpenSocket`, `SocketOption` or `CloseSocket`, `ManagedCurlEngine.PoolOf` puts a `SocketCallbackConnector` beneath the pool (`PoolingConnector.Over`, for the `TcpConnector` and FTP's data connector alike) and `CreateConnectOnlyConnector` wraps its `TcpConnector`; with none set nothing changes. Before each TCP attempt dials, the connector's `AttemptSocketOpener` (the target's `SocketOpener`, ADR-0903) asks the open-socket callback for a socket with `CurlSocketType.IpConnection` and the attempt's address (`SocketCallbackConnector.AddressOf`), `CurlSocket.Bad` making no connection and failing with exit 7, and a returned socket being the one the dialer connects; without it, when the socket-option callback is set and the dialer adopts sockets (no `EngineDialing`), the opener opens an operating system TCP socket itself before the connect, with `TCP_NODELAY`, hands that handle to the socket-option and close-socket callbacks and to the dialer as a supplied socket (connected, or used unconnected under `AlreadyConnected`, so the first send fails with exit 55), and closes it after the close-socket callback (`CurlSocketCloser`'s owned socket; CGR-145, ADR-0845); otherwise the dialer opens its own, which the socket-option callback sees as the engine's next `CurlSocketHandles` number (`ManagedEngineSharedState.SocketHandles`) and the close-socket callback as the connection's operating system socket (`IConnection.SocketHandle`), called before the engine closes it so the callback sees it open (that number when the connection has none; CGR-129, ADR-0842). The socket-option callback comes next, `SocketOptionResult.Error` calling close-socket and failing with exit 42, both as `Failed to connect to <host>:<port> after <n> ms: <text>`, and `AlreadyConnected` using the returned socket as it is; a failed attempt's socket goes to close-socket (CGR-036, BL-3565, ADR-0831). The connection is a `SocketCallbackConnection`, which forwards every member and calls close-socket once (`CurlSocketCloser`) when it is disposed (ADR-0610). A QUIC connection (`ConnectMultiplexedAsync`) goes through the same steps, the open-socket callback seeing `SOCK_DGRAM` and `IPPROTO_UDP` (`DatagramAddressOf`), and is a `SocketCallbackMultiplexedConnection` that calls close-socket once when disposed; `ConnectMultiplexedSessionAsync` builds the session over it, so the pool above still shares one session (BL-2474, ADR-0660). Their tests are `SocketCallbackConnectorTests` and `ManagedEasyTransferTests.Sockets.cs`.

FTP's active-mode (`CURLOPT_FTPPORT`) listener goes through a `SocketCallbackConnectionListener` when the handle sets the open-socket, socket-option or close-socket callback (`CreateDispatcher`'s `ftpListener`, over `EngineDialing.FtpListener` or a `TcpConnectionListener`): the open-socket callback is asked for the listening socket once it is bound (`CurlSocket.Bad` stopping it, exit 30 `socket failure`), and close-socket is called once when the peer is accepted or the listening stops; the accepted connection gets neither, as curl 8.22.0's `ftp_state_use_port` and `cf_socket_close` (upstream test596, BL-2588), but the socket-option callback is asked for it with `CurlSocketType.Accept`, and its `SocketOptionResult.Error` closes it and fails the accept with exit 42, as `cf_tcp_accept_connect` (upstream test766, BL-2638). Its tests are `SocketCallbackConnectionListenerTests`.

## The WebSocket API (BL-2443)

A perform from the options with `EasyNetworkOptions.ConnectOnly` set to `WebSocket` (`CURLOPT_CONNECT_ONLY` 2) of a `ws` or `wss` URL runs the normal perform path over a dispatcher of one `WebSocketUpgradeOnlyHandler` (`FollowerOf`, `WebSocketUpgradeDispatcherOf`): a `WsProtocolHandler` over `CreateConnectOnlyConnector`'s connector, authenticating with `ManagedCurlEngine.CreateWebSocketAuthenticator`, whose `ConnectAndUpgradeOnlyAsync` hands the open connection and the bytes after the `101` head to the handle's `ManagedEasyWebSocket`, which `WebSocket` answers; a refused upgrade answers the transfer's code and keeps nothing, except that a server closing before the reply head ends answers `Ok` with no upgraded connection, as curl 8.22.0's `Curl_http_done` skips its empty-reply check under `connect_only` (upstream test2304, BL-2712, ADR-0705). For any other scheme `WebSocket` only connects, as `Connect` (`IsRawConnectOnly`). `ReceiveAsync` never waits: one read at a time, `Again` while it runs or while only part of a frame has come, then the first run `WsFrameMetadataDecoder` gave, as much as the buffer holds, with `WebSocketFrameFlags.Of`'s bits (a continuation reports its message's type, `Continuation` while FIN is clear), the offset and the bytes left; `GotNothing` when the server closes, `RecvError` for a failed read or a protocol violation, from then on. Each completed ping is answered with a pong unless `EasyWebSocketOptions.Options` has `NoAutoPong` or `RawMode`, and only under those bits is the ping handed to `ReceiveAsync`: an answered ping never is, as `lib/ws.c` keeps it from the application (upstream test2708, BL-2782). Under `RawMode` (`CURLWS_RAW_MODE`) `SendAsync` writes the bytes unframed and refuses any bit or fragment size with `BadFunctionArgument`, as `lib/ws.c` does, while `ReceiveAsync` still decodes frames, as `curl_ws_recv` does (BL-2444); a perform that is not connect-only gives `WsProtocolHandler.RawMode` the same bit (`ManagedCurlEngine.IsWebSocketRawMode`, `EngineComposition.CreateProtocolHandlers`' `webSocketRawMode`), so the write callback gets the received stream unframed (BL-2494). `SendAsync` writes one masked frame, the opcode from `WebSocketFrameFlags.TryFrameOf` (`BadFunctionArgument` for bits libcurl refuses), `SendError` when the write fails. `CurrentFrame` is the frame last handed over, `null` before any. With options no longer connect-only both answer `UnsupportedProtocol`, and with no upgraded connection `BadFunctionArgument`. Under `CURLWS_OFFSET` the first sends fragment size is the whole payload, which the head announces, and every send continues that frame until its payload is all sent, each part masked at its offset (`WsFrameEncoder.EncodeHead` and `MaskPart`); a part longer than what is left is `BadFunctionArgument`. `StartFrameAsync` (`curl_ws_start_frame`) writes a frames head for the sends to fill: `FailedInit` under `RawMode`, `SendError` with no connection, a frame unfinished or a negative length, the same inside a read callback or out, as `lib/ws.c` checks none (BL-2481, ADR-0665). On a perform that is not connect-only, a read-callback upload's `CallbackReadStream` carries the handle's `ManagedEasyWebSocket.UploadFrames`, so `WsProtocolHandler` sends each read as one binary frame, as `cr_ws_read` does, and `StartFrameAsync` called from the read callback starts the frame the following reads fill (`SendError` outside an upload being sent or while a frame is unfinished, `BadFunctionArgument` for bits naming no frame) (BL-2611, ADR-0669). The internal `WebSocketRandomSource` (`SystemWebSocketRandomSource` by default; `Duplicate` copies it) gives the masks and the key. During a perform that is not connect-only, `SendAsync` writes to the connection that perform's frames flow on, which the handle's `ManagedEasyWebSocket.PerformConnection` (the dispatcher factory's sixth argument, `CreateDispatcher`'s `webSocketPerformConnection`, given to `WsProtocolHandler.PerformConnection`) shows from the `101` until the transfer ends, so a write callback's `curl_ws_send` reaches the server as libcurl's does (upstream test2301, BL-2710); outside that window it answers as before. On such a perform the handler writes each frame's run of payload alone and shows it there first (`WsPerformConnection.Frame`, with the message's `MessageOpcode`), and with options not connect-only `CurrentFrame` is that frame (bits, offset, bytes left, length), so a write callback's `curl_ws_meta` answers it as libcurl's `ws->recvframe` (upstream test2302, BL-2711). Every perform and `DisposeAsync` close the connection (ADR-0616). Their tests are `ManagedEasyWebSocketTests` and `WebSocketFrameFlagsTests` (over `QueuedConnection`, whose reads take queued chunks) and `ManagedEasyTransferTests.WebSocket.cs`.

## The HSTS read and write callbacks (BL-2421)

## The SSH key callbacks (BL-2422)

## The cookie list (BL-2520)

A perform from the options with no `ToolInputs` applies `EasyHttpOptions.CookieList` (`CURLOPT_COOKIELIST`) in `SetUpAsync`, in the order set, before the cookie files load (`CookieEngine.ApplyCookieListAsync`), as curl 8.22.0's `cookielist` in `lib/setopt.c`: `ALL` is `CookieStore.RemoveAll`, `SESS` `RemoveSessionCookies`, `FLUSH` writes the jar, `RELOAD` loads every cookie file again, each command in any case; any other item is a Netscape or `Set-Cookie:` line read as a cookie file's line, and turns the cookie engine on (`CookieEngine.TurnsTheEngineOn`). ## Per-handle caches (BL-3271)

`CreateEasy` and `CreateMulti` each take `ManagedEngineSharedState.WithOwnCaches()`: the engine's clock, numbering, multi owners and performer with an empty connection pool, TLS session cache, DNS cache, cookie store and HSTS cache of their own, as libcurl gives each easy and multi handle; a new handle so looks a name up again and calls its `CURLOPT_RESOLVER_START_FUNCTION`, whose abort answers `CurlCode.AbortedByCallback` (CGR-151, ADR-0851; `Cgr151Tests`). `MultiCaches` keeps each multi handle's state. `ManagedEasyTransfer.PerformShared` runs a perform over its share handle's caches, else `EngineWide` under `ToolSettings` (the curl tool), else, while the handle is in a multi handle, the multi's connections, TLS sessions and resolved names with the handle's own cookies and HSTS (`InMulti`), else the handle's own; `DisposeAsync` closes the idle connections it owns in the pool it used. `Duplicate` takes `DuplicatedWithOwnCaches`, fresh caches whose HSTS cache starts with the source's entries (upstream test1922).
