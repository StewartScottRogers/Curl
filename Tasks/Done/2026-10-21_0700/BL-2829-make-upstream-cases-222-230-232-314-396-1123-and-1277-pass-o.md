# BL-2829 — Make upstream cases 222, 230, 232, 314, 396, 1123 and 1277 pass on Windows: the included XML file after a deflate reply

## Goal

Upstream cases 222, 230, 232, 314, 396, 1123 and 1277 pass on Windows (as the gap office already measures them `match` on Linux) and are on `Curl.Conformance.UnitTests/PassingUpstreamCases.txt`.

## Context

Each case sends a compressed reply and expects `curl --compressed` to write the decoded document, which the case supplies with `%includetext %SRCDIR/data/data-xml1` (or `data-xml2`) in `<datacheck>`. Measured 2026-10-19 on Windows, all seven fail the same way: `the --output file against <reply><data> differs at byte 278 to 306: expected the end, got "<?xml version=\"1.0\" encoding=\"ISO-8859-1\"?>\n"` - the output holds the XML document one more time than the case expects, or the expected side lost its included text. The same cases are `match` on Linux. So the likely cause is Windows-only: the `%includetext` expansion (`Curl.Conformance.UnitLibrary/UpstreamTestFileInclusions.cs`, `%SRCDIR/data/...` path handling, line endings of the included file) or the decoder. Find which with `CURL_UPSTREAM_KEEP_LOGS=1`, which keeps the case's log folder (`curl<n>.out`, `stdout<n>`).

Cases (all include `data-xml1`): 222 (deflate), 230 (multiply compressed), 232 (raw deflate), 314 (brotli), 396 (zstd), 1123 (deflate transfer-encoding), 1277 (content and transfer encoding together).
Upstream: curl 8.22.0 `tests/data/test222` and the others. Where the product (decoder) is wrong, fix it and add a focused unit test in that library's own `.UnitTests` project (ADR-0482); where the harness is wrong, fix `UpstreamTestFileInclusions` and pin it in `UpstreamTestFileExpanderTests`. If the fix is in a library other than the two named in `touches`, add its folder to this task's `touches` in the same commit.
