# BL-1645 — Make X25519 and X448 five times faster than before BL-1525 with 64-bit-only field arithmetic

## Goal

`Curl.Cryptography.UnitLibrary`'s X25519 and X448 key exchanges run at least five times faster than the sources from before BL-1525 (commit `b51e4e59f`'s `Curl.Cryptography.UnitLibrary`), still constant-time and bit-exact, so their RFC 7748 section 5.2 million-iteration Integration tests take minutes.

## Context

- Split from BL-1525 (2026-10-07), which landed CAST-128's speed-up (about 7x) and the first curve speed-up: `Field25519` on 5 x 51-bit limbs, `Field448` on 8 x 56-bit limbs, both accumulating 128-bit column sums in `Accumulator128`; bench ratio against the old sources about 2.9x for X25519 and 2.6x for X448. Read BL-1525's Notes first: they hold every measurement, the JIT disassembly findings and the bench method.
- What still costs time (BL-1525 lane 4): `Math.BigMul`'s `out ulong` low half goes through memory and the ten 128-bit accumulators spill; `Accumulator128.AddHalves` computes each carry with about six bit operations.
- Likely next steps: 64-bit-only arithmetic whose products need no 128-bit sum - radix 2^25.5 in 10 limbs for 2^255-19 (ref10's `fe_mul`/`fe_sq`), and 16 x 28-bit limbs with Hamburg's Karatsuba for 2^448-2^224-1 - or `X86.Bmi2.X64.MultiplyNoFlags` / `ArmBase.Arm64.MultiplyHigh` with the portable path kept beside them.
- The machine running the dark factory is loaded by up to nine lanes, so absolute timings drift by 2x. Judge speed by the ratio of the old and new sources benchmarked back to back in one run (BL-1525's bench: two throwaway console projects in %TEMP% compiling the library's `*.cs`, Release, best of 5 rounds).
- Constraints: no secret-dependent branch or index, no allocation in field arithmetic, BCL only, portable on x64 and Arm64; Ed25519/Edwards25519 also use `Field25519` and must keep working unchanged.

## Acceptance criteria

- [x] Notes record a back-to-back Release benchmark of the pre-BL-1525 sources and the new ones in one run, showing X25519 and X448 each at least 5x faster per operation.
- [x] Every test in `Curl.Cryptography.UnitTests` passes unchanged, Integration tests included (`dotnet test Curl.Cryptography.UnitTests -c Release --filter "TestCategory=Integration"`), with their durations recorded in Notes, and the fast tests of the whole solution pass.
- [x] Each changed field class's doc comment states it has no secret-dependent branch or index, and the review stage checks it.
- [x] `Measure-CodeQuality.ps1 -Library Curl.Cryptography.UnitLibrary` reports 100% line and branch coverage with no member over complexity 10 or CRAP 30, and `dotnet build -warnaserror` is clean.

## Notes

- 2026-10-07, lane 4:
  - Plan taken: 64-bit-only field arithmetic, no 128-bit sums. `Field25519` now holds 10
    signed limbs in radix 2^25.5 (26/25 bits, ref10's layout): 100 plain products per
    multiply, 55 per square, odd x odd products doubled, products past 2^255 folded with
    19. `Field448` holds 16 limbs of 28 bits: 256 products per multiply, 136 per square,
    31 column sums folded with 2^448 = 2^224 + 1 straight into the result, then carried
    in place. The unrolled column sums were generated by a throwaway PowerShell script in
    %TEMP% and pasted. `Accumulator128` is gone (nothing else used it). No public or
    internal signature changed; `LimbCount` is 10 and 16, and every caller (X25519, X448,
    Edwards25519, Edwards448, the tests) only uses the API.
  - Bounds: Field25519's column sums stay below 2^62 for inputs that are sums or
    differences of up to three carried elements (Edwards25519's point addition's
    worst case), so its Add and Subtract stay uncarried. Field448's Add and Subtract carry
    their result: without that carry the X448 tests for p + 1 and p + 5 peer keys failed
    (a column sum overflowed), so the carry stays and costs a few percent. Field448's
    Encode now adds 4p before carrying, so a value with negative limbs never folds a
    negative top carry back in.
  - Bench (BL-1525's: two throwaway console projects in %TEMP%, `bl1525head` compiling
    the sources from before BL-1525 and `bl1645work` compiling this checkout's
    `Curl.Cryptography.UnitLibrary*.cs`, Release, best of 5 rounds; outputs
    bit-identical, `422C8E7A 3F482C8A`), three back-to-back pairs on the loaded machine:
    X25519 474.3 / 477.4 / 476.9 us -> 57.1 / 56.3 / 58.1 us (8.3x / 8.5x / 8.2x);
    X448 1673.2 / 1669.7 / 1680.7 us -> 412.2 / 324.8 / 333.5 us (4.1x / 5.1x / 5.0x).
    Best of the three pairs: X25519 8.5x, X448 5.1x. X448 is at the edge of the target:
    one pair under load came out at 4.1x. If more is wanted, Hamburg's Karatsuba on
    2^224 (192 products instead of 256) is the next step.
  - Integration TRX, `dotnet test Curl.Cryptography.UnitTests -c Release --filter
    "TestCategory=Integration"`, all 5 pass, 5 m 42 s in all: X25519 million iterations
    1 m 03 s (BL-1525's lane-4 figure 7 m 21 s), X448 million iterations 5 m 42 s
    (27 m 23 s), CAST-128 B.2 16.1 s, the two Wycheproof brainpool runs 1.8 s and 0.9 s.
  - All 1445 fast tests of Curl.Cryptography.UnitTests pass unchanged; the whole
    solution's fast tests pass (33 test projects, 0 failures); `dotnet build -warnaserror`
    clean; `dotnet format --verify-no-changes` clean on the library.
  - `Measure-CodeQuality.ps1 -Library Curl.Cryptography.UnitLibrary`:
    `| Curl.Cryptography.UnitLibrary | 100 | 100 | 771 | 0 | 10 |`.
  - Review of criterion 3: both field classes' doc comments state they are constant-time
    with no branch, loop bound or index depending on an element's value. Checked by hand:
    every loop runs over public limb indices; `LimbStart`/`LimbMask` and the
    `index == MiddleLimb` choices depend on the public index only; carries are shifts and
    masks; the final subtraction picks by `ConditionalSwap`'s mask; no allocation.
