# Adversarial testing

The method every per-project adversarial black-box test task follows (BL-1491). Stewart
asked on 2026-10-06 for aggressive black-box testing of every `*.UnitTests` project:
boundaries, malformed input, attacks on the invalid partitions, and state and
concurrency stress. One task per test project applies it, after every other open task
that changes that project's tests is done; this page is what each of them works to, so
every library is attacked the same way and to the same rules.

## What black box means in Curl

An adversarial black-box test attacks a library through its public surface only, with
inputs chosen to break it, and checks the answer against an oracle rather than against
the code's own idea of what is right.

- **The surface** is the library's public types and members, and for `Curl.Console` the
  command line: arguments in; standard output, standard error, written files and the exit
  code out. A test never reaches an `internal` member, a private field or reflection to
  set up or check a case.
- **The oracle** is real curl wherever the behaviour is visible on the command line.
  Measure the expected bytes and exit code with `Record-CurlExchange.ps1` - the Schannel
  build on Windows, the OpenSSL build on Linux and macOS - and pin what it printed. Never
  pin an answer guessed from what curl "implies" or from Curl's current output. Where
  curl's answer differs by platform, pin each platform's answer in its own test.
- **Below the command line**, where curl shows no direct answer (a parser, a cipher, a
  record reader), the oracle is the specification the library implements - the RFC, its
  test vectors - and the library's own documented contract: a refusal it names, never a
  crash, a hang or an exception type its doc comment does not promise.

## The four attack families

The generic attack list translates to curl like this: SQL injection and cross-site
scripting hardly apply, because Curl renders nothing and queries nothing. CRLF header
injection, URL-parser confusion, path traversal through `-O` and `--output-dir`,
config-file parsing, and malformed protocol and crypto records do.

### 1. Boundaries

Every limit, on both sides and exactly on it: the value just inside, the value itself,
the value just outside.

- Numbers: `--max-time 0`, a negative value, the largest `long` and one past it,
  `--range 0-0`, `--limit-rate 1`, a port of 0, 65535 and 65536, `--retry` at the int
  limit.
- Lengths: an empty URL, host, header name, header value, user name and password; a
  host label of 63 and 64 bytes; a host name of 253 and 254; a header line at the
  library's buffer size and one byte past it.
- Counts: zero, one and many of anything repeated - `-H`, `-d`, URLs, globs
  (`[1-1]`, `[0-0]`, `{}` and the glob limits curl enforces), redirects at `--max-redirs`
  and one past it.
- Protocol fields: a `Content-Length` of 0 and of `long.MaxValue`, a chunk size of `0`
  and one that overflows, an FTP reply code of 099 and 600, a TLS record of exactly
  2^14 bytes and of 2^14 + 1, an SSH packet at its maximum length.

### 2. Malformed input (semantic fuzzing)

Input that is almost right - one field wrong - generated by hand from valid input, so it
gets past the first check and reaches the code behind it.

- Command line and config file: an unterminated quote in a `-K` file, a `--` inside a
  value, a long option with `=` and no value, invalid UTF-8 and a NUL in an argument,
  a config line with only whitespace, a `url = ` with nothing after it.
- URLs: `http://user@:80@host/`, two `@`, a scheme with no `//`, an IPv6 literal with no
  closing `]`, percent-escapes cut off (`%4`), a backslash where curl expects `/`, a
  Windows drive letter in a `file://` URL on Linux and macOS.
- Headers: CRLF injected into `-H`, `-A`, `-e` or a cookie value (`"x\r\nEvil: 1"`), a
  bare LF, a header with no colon, a folded continuation line, a status line with no
  reason phrase or a three-digit code followed by garbage.
- Output paths: a `-O` file name from the URL or `Content-Disposition` that is `..`,
  `../x`, absolute, or holds a NUL or a drive letter, and the same joined with
  `--output-dir`.
- Protocol and crypto records: a truncated record, a length field larger than the data,
  a length of zero where one is required, an unknown type or extension, a duplicated
  extension, a bad padding byte, a MAC or tag one bit wrong, a point not on the curve, a
  DER length in the long form for a short value.

### 3. Invalid partitions

Split each input into equivalence partitions and attack every invalid one, not only the
first, with at least one representative of each: below range, above range, wrong type,
wrong format, wrong encoding, and conflicting combinations.

- Option values: `--max-time abc`, `--max-time 1e999`, `--max-time -1`, `--retry 1.5`,
  `--proto =bogus`, `--http2 --http0.9` style contradictions, `-T` with `-d`.
- URLs by scheme: a scheme Curl does not know, a known scheme with the wrong default
  port syntax, a scheme in the wrong case, a URL with credentials for a scheme that
  takes none.
- Server replies by state: a reply valid in one state sent in another - a `226` before
  `150` in FTP, a `CONTINUATION` frame with no `HEADERS` before it in HTTP/2, an SSH
  message before key exchange finished.

Each partition gets its own test, so the test name says which invalid zone it attacks.

### 4. State and concurrency

Drive the library through orders and timings its happy path never sees.

- Order: call a method twice, call it after `Dispose`, read before connect, write after
  the peer closed, reuse a parser after it refused input.
- Partial delivery: feed a reply one byte per read, split at every offset of a
  multi-byte field, end the stream in the middle of a record, return zero bytes before
  the end.
- Time: advance an injected `TimeProvider` past a timeout during a read, exactly to the
  timeout, and backwards; never sleep.
- Cancellation: cancel the token before the call, during it, and after it finished.
- Concurrency: run the same public call on many tasks at once against shared state the
  library claims is safe (a cookie jar, a connection pool, a cache) and check the
  result is the same as running them one after another.

## The rules

- **Public surface only.** No `InternalsVisibleTo` added for these tests, no
  reflection, no private state.
- **Injected fakes, never a real network.** Use the fakes the library already takes:
  `IConnection` for bytes on the wire, and a hand-written `TimeProvider` subclass (the
  one the test project already has, or a new one in it) for time. No socket, no loopback server, no DNS; `Record-CurlExchange.ps1`
  is run by hand to measure curl, and only its result goes into a test.
- **MSTest and the base class library only.** No fuzzing, property-testing, mocking or
  assertion package. Generators are hand-written in the test project: a seeded
  `System.Random` with the seed fixed in the test, so a failure reproduces, and the seed
  printed through `TestDiagnostics` when the test fails.
- **Every test passes on Windows, Linux and macOS.** No drive-letter path, Windows-only
  error text or certificate outside a test marked
  `[OSCondition(OperatingSystems.Windows)]`; where curl answers differently by platform,
  one test per platform's answer.
- **Large inputs stay out of the fast run.** An input over 1 MiB is either streamed
  (generated as it is read, never held in one array) or the test is marked
  `[TestCategory("Integration")]`. Every test still keeps to the 3000 ms budget
  [Test diagnostics](Test-Diagnostics.md) reports as `SLOW:`.
- **Test names say what they attack.** `Parse_ChunkSizeOverflowingLong_RefusesWithoutThrowing`,
  not `Parse_Fuzz3`. A one-line comment says why only where the name cannot - for
  example which curl version and build the pinned bytes were measured on.
- **The quality gates still hold.** The new tests sit in the library's existing
  `.UnitTests` project and count toward its 100% line and branch coverage.

## When a test breaks the library

- **A red test is never committed.** The fast tests stay green on every commit.
- **The defect is filed as a follow-up task** with the board script, naming the library,
  the input and what happened. It is **High** when it is a crash, a hang, a memory
  blow-up or a security issue (secret in output, path escaping the output directory,
  injected header reaching the wire); Normal otherwise.
- **The test lands with the fix,** in the follow-up task, not in the adversarial task
  that found it. The adversarial task records the filed task's ID under its Notes and
  carries on with the next attack.

## What the audit office already does

The audit office
([ADR-0267](../Planning/Decisions/ADR-0267-an-independent-audit-office-audits-the-dark-factory-from-outside-its-reach.md))
audits from outside the factory, periodically: `audit-security` fuzzes the hand-built
cryptography, TLS, SSH and QUIC parsers and looks for timing leaks and secrets in
output; `audit-conformance` runs generated command lines through real curl and Curl and
reduces every difference. Those audits report findings; they leave no tests behind.

The per-project adversarial tasks do not repeat those audits. They add **permanent
tests** to the project's `.UnitTests`, so every attack that once mattered runs on every
commit on all three platforms. A finding the audit office reports is a good source of
attacks; its fix and test arrive through the finding's own task.
